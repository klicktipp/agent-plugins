# KlickTipp account setup

Bring the customer's **selected account** from its current state to the smallest usable setup for their stated goal. Start with what already exists. Carry forward confirmed answers; ask only for missing decisions that affect the next step. A homepage may suggest audience and offer, but present those as assumptions until the customer confirms them.

For a readiness question, inspect and report without changing the account. During guided setup, handle one unresolved decision at a time; a specialist may group fields for one decision. Show the current finding and actual candidates before asking; never rely on unseen numbered references. If the goal is missing, ask for it before reading the account. Otherwise state the next check, then use only the reads needed for that step.

## Establish scope and access

- Identify the selected account and whether the customer wants MCP access, sending readiness, or both. A successful sign-in is not proof that this account may use AI/MCP. A skill cannot itself make a chat open automatically after plugin installation; treat any proposed onboarding gate as a separate client capability to verify.
- Read the current account/capability response and its live tool contract. Treat product-provided eligibility, available plan, required plan, upgrade destination, and retry guidance as the source of truth. Do not infer entitlements from a plan name or from `validate-account-sending-readiness`.
- If the product explicitly says this account may upgrade to enable MCP, say so plainly and give its returned upgrade link in text. Explain that the customer must complete the account change; do not book or purchase on their behalf.
- If the refusal concerns authentication, account selection, permissions, a blocked account, a limit, or a temporary error, explain that actual issue and its supplied remedy. Do not present an upgrade as the fix unless the product response confirms it.
- After the customer reports an upgrade, retry a suitable read-only access check. If access is not yet available, use the current response to explain whether to reconnect, wait, or contact support. Never ask for a password, API key, billing data, or a screenshot of secrets in chat.

When account capability details are unavailable, state what can be verified and what is missing. Do not invent current prices, tariff rules, or a generic checkout URL. Keep the guidance usable in clients without widgets.

## Build on the existing setup

1. For an email-sending goal, read account settings and `validate-account-sending-readiness` first. Inspect only the sender domain, sender address, signatures, opt-in processes and contacts needed for that goal. Treat `readyToSend` as technical account readiness only; it does not prove that placeholder-backed company, address or contact data is populated.
2. Reuse a verified sender path. When a domain or URL is known, pass its hostname to `dns-setup` immediately and let it inspect public NS records before asking where DNS is managed. Treat the result as the likely authoritative DNS host, not the registrar or proof of an editable account; ask only when the lookup is unavailable or ambiguous. If the intended path needs a missing or invalid domain, use `dns-setup` before test send or dispatch. If the proposed address is Gmail, GMX, web.de or another freemail address, ask for the customer's own sending domain. If it is unknown, ask for the company homepage to identify a candidate. A homepage supplies context but does not replace a sending domain. A product-enforced domain security wait is mandatory; continue only independent preparation until a live read confirms activation.
3. After the domain decision, confirm which company or brand this marketing work is for. Treat readable account data and verified domains as candidates, not identity proof. Use `company-context` to confirm the website and context source. The reusable profile may be skipped; then collect only the task facts needed by the requesting content skill.
4. Only after the company context or task brief is confirmed, use `signatures` to inspect or choose the visible sender identity and signature. Require its handback to verify the rendered company identity, postal address and contact paths. Unreadable or incomplete values block sending, not draft work. Registering a sender address sends a real confirmation email; explain that effect and obtain approval before creation.
5. Inspect the default opt-in process before a new signup route uses it. Verify sender, confirmation email, redirects and consent scope through `opt-in`; do not infer consent from the company profile.
6. Ask whether the customer already has contacts, and where they are. Reuse contacts already in KlickTipp. For an external CSV or Excel list, ask about its source, columns and consent/status markers without requesting the whole file merely to plan setup. When the customer wants the list checked or imported, use `contacts` and its `references/contact-import.md` for classification, mapping and the supported import path; use `opt-in` for DOI process details. A one-contact upsert is not a bulk import. If no contacts exist, route lead capture by placement: the KlickTipp app for an external-site embed form or a KlickTipp-hosted landing page, or the `manage-klicktipp-forms` skill for the KlickTipp WordPress plugin. If `manage-klicktipp-forms` is unavailable, mark that path blocked instead of substituting another form workflow. More than one route may be needed.
7. For a first one-time newsletter, hand audience, sender, test and dispatch to `newsletter`, body and preview to `email`. For an ongoing or repeatable campaign, hand the flow to `automation` and each message's content to `email`. Use an isolated permitted test recipient. Creating a contact or sending a test can trigger real email, tags, or automations; agree on that effect before execution. Report draft, published, test-sent, scheduled, active and sent as distinct states.

Check current tool schemas before mutations and read back the resulting state. If a tool or account does not expose the required operation, offer a concrete app step or mark the part unverified. Do not claim setup complete from a clean body validator or from a schema description alone.

## Completion report

Summarize the selected account, goal, marketing company, sender path, company-context status, technical readiness, rendered identity, MCP access, completed actions, blocks and next customer action. Mark the result as `setup_complete`, `setup_complete_activation_pending` or `setup_blocked`. Unverified identity makes a sending goal `setup_blocked`; draft-only work may continue. Never present an activation-pending account as send-ready.
